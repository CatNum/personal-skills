# md-formatting

## 目标

统一 Markdown 的标题、重点和正文层级，同时让文档内容服从其写作目的。
以下通用规则始终适用；不同类型的内容与章节细则按需读取
`references/`，不要一次加载全部。

## 判断类型并读取细则

先看用户明确指定的类型，再看文档实际回答的问题，
最后参考文件名或目录名。只读取命中的类型文件：

| 文档目的 | 读取 |
| --- | --- |
| 博客：观点或经历 | [`blog.md`](references/blog.md) |
| ROADMAP：版本总览 | [`roadmap.md`](references/roadmap.md) |
| 产品文档：功能与规则 | [`product.md`](references/product.md) |
| 设计文档：内部方案与逻辑 | [`design.md`](references/design.md) |
| 个人学习笔记 | [`notes.md`](references/notes.md) |
| 术语表 | [`glossary.md`](references/glossary.md) |

若一份文档确实兼有多个目的，只读取相关细则，
以主要读者和主要问题确定主类型；
内容可独立维护时，建议拆分并互相链接。
产品文档、设计文档或 ROADMAP 涉及共用术语时，
额外读取 `references/glossary.md`。
类型仍无法可靠判断时，先只用通用规则保留原结构；
类型会改变实质内容取舍时向用户确认。

## 通用格式

1. 全文只有一个顶层 `# 标题`，并以它作为第一个标题。
   保留原题含义；缺少标题时从明显的标题文本、
   文件名或首段主题推断。仍无法确定时用
   `# 待确认标题`，在重点中说明。
2. `## 重点` 只出现一次，紧接在顶层标题后，
   位于正文标题之前。使用 bullet 列表，每条以加粗的
   关键信号短语开头，接一到两句独立可读的说明；
   数量按内容决定。重点只能提炼已有信息，
   不编造事实、数字、状态或结论。
3. 正文标题按需设置，不生成空章节。`##` 使用连续的
   中文序号，如 `## 一、背景`；`###` 使用所属章节的
   编号，如 `### 1.1 现状`；`####` 使用
   `#### 1.1.1 原因`。同级递增，不跳号、不重复，
   只在需要时加深层级。
4. 关系或流程用图能明显改善理解时，先写一句图意说明，
   再给出带 `mermaid` 语言标记的代码块。
   已有代码块、表格除明显损坏或缺少必要格式外尽量保留；
   代码块不强制添加语言标签，表格保证正确和可读即可。

基本结构：

```markdown
# <标题>

## 重点

- **<关键信息>**：<来自文档的简短说明>。

## 一、<正文主题>

<正文>
```

## 段落与分点

所有文档类型都按内容关系组织段落和列表：

- 每个段落围绕一个主要主题展开。主题、论点或叙述阶段改变时，
  用空行分成新段；较长说明可按结论、原因、例子分别展开，
  避免把多个独立主题塞进同一段。
- 源码中的普通换行仍属于同一段；真正分段需要空行。
  不用机械地拆句或每句单独成段代替内容组织。
- 并列的规则、特性、职责、选项和注意事项使用 `-` 无序列表；
  有先后顺序或依赖关系的操作步骤、流程使用 `1.` 有序列表。
  连贯的解释和论证用段落展开，不把所有正文都变成列表。
- 每条列表项承载一个要点或步骤，先写核心内容再补解释。
  列表项较长时可以在项内分段，续行和后续段落保持正确缩进；
  只有存在明确的包含关系时才嵌套列表。
- 标题、段落和列表之间保留必要空行；较长的内容块按主题加小节，
  避免连续堆积大量列表项。

## 语义标识与强调

所有文档类型都按文字的含义选用标识：

- **加粗**：突出核心结论、关键规则、设计决策、限制条件，
  或术语表中的标准名称。优先加粗关键词和短语；
  不把整句、整段或每个列表项都加粗。
  `## 重点` 中每条 bullet 的关键信号短语保持加粗。
- **行内代码**：用于需要精确识别的技术文本，
  如字段名、函数名、命令、文件路径、配置值和接口路径。
  不用它强调普通概念或整句说明；
  介绍字段、函数时，同时解释名称含义与实际作用。
- **代码块**：承载多行代码、命令、配置和 Mermaid 图。
  不把普通说明段落放进代码块来突出显示。
- **引用块**：用 `>` 标识原文摘录，
  使引用内容与作者自己的解释清楚区分；保留来源依据。
- **链接**：连接资料来源、相关文档和共用术语定义；
  链接文字应说明目标内容，避免只有“点击这里”。
- **删除线**：用 `~~删除线~~` 标识明确已废弃的旧方案；
  当前有效的规则与方案正常书写。

标题、列表和表格负责组织内容，加粗提示优先阅读的位置，
行内代码标识应原样理解的文本。中文文档不默认使用斜体；
`==高亮==` 等扩展语法仅在目标阅读器明确支持且用户需要时使用。

## 源码可读性与换行

- 正文段落和列表项要便于在 Markdown 源码视图、窄窗口及差异视图中阅读。
  新写或整理时主动将过长的物理行换行，避免依赖水平滚动。
  默认以约 80 个显示列为参考（中文和全角字符通常占 2 列，
  英文、数字和半角符号通常占 1 列）；
  项目已有行宽约定或展示窗口更窄时，按实际情况调整。
- 优先在句号、分号等语义停顿处断行，不拆开词语、链接或行内代码。
  普通换行只用于整理源码；除非内容本身需要固定的显示换行，
  不添加行尾双空格或 `<br>`。
- 列表项可以跨多行，续行缩进到列表正文的位置。
  `## 重点` 中的每条 bullet 也遵循此规则，不能因一句话过长而写成单个超长物理行。
  例如：

  ```markdown
  - **组件分工**：网页负责计划与重置会话；
    服务侧负责调度和选择执行位置；
    本机与云端执行器分别承担任务执行。
  ```

- 长标题应精简；表格单元格无法安全地在源码中换行时，
  改用列表或小节承载长段说明。代码块按语言语法整理，
  不为满足行宽而破坏代码；长链接优先使用简短的链接文字。

## 旧文更新

- 即使只改动一小部分，也检查全文是否有单个顶层标题、
  紧随其后的唯一 `## 重点`，并让重点反映当前内容。
- 检查最终文档中的正文和列表物理行；对超长行按上述规则换行，
  保持原意与 Markdown 结构，不把一条列表拆成多条。
- 保留原意、已知事实、未决状态、正文措辞与标题深度；
  主要做必要的区块补齐、编号和轻量重排。
  编号只改变标题文字，不要求改变层级。
- 仅当多个 `#`、跳级标题或新增 `## 重点` 使正文
  错误归入重点之下，或用户明确要求重组时，
  才最小幅度调整层级。例如原文在 `#` 后直接使用
  `###` 正文标题时，将其提升到 `##`。调整后检查文内链接。
- 缺少某类型常见内容时，不按模板补写未知事实。
  必要信息缺失且影响任务完成时向用户确认；
  可继续处理的部分先完成，在交付说明中指出缺口。

## 输出与自检

- 在对话中直接输出格式化后的 Markdown 文档、
  且用户未要求说明时，只输出文档。
  修改文件、讨论写法或修改本 skill 时，按请求说明
  改动与未决事项；若用户同时明确要求贴出全文
  或只输出文档，以该要求为准。
- 输出前检查：类型细则是否按需读取；
  标题与重点是否唯一且顺序正确；重点是否有来源依据；
  编号是否连续；正文与列表是否存在需要水平滚动的
  超长物理行；是否保留旧文语义；
  是否产生空章节或虚构内容；
  段落是否各有主题；并列要点与顺序步骤是否使用合适的列表；
  分段空行和列表缩进是否正确；
  加粗是否聚焦关键短语；行内代码是否用于精确技术文本；
  引用、链接与删除线是否表达对应含义；
  代码块、表格和 Mermaid 是否可读。
