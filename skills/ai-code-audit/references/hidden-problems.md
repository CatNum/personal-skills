# 隐形问题分类与检查方法

每类按“核心约束 → 失效机制 → 检查方法 → 修复原则 → 验证维度”组织。按代码证据选择相关条目，类别重叠时明确主根因与受影响约束。

## 一、性能与依赖

- **核心约束**：关键路径只等待产生正确结果所必需的工作，工作量与影响范围匹配。
- **失效机制**：独立调用被串行执行；同一意图重复请求；局部变更触发全量同步；可选依赖阻塞必需结果；重复计算或无界读取放大成本。
- **检查方法**：绘制依赖图，区分因果、身份、版本依赖与独立工作；测量首次反馈、关键结果可用与全部完成的时间，核对调用次数、数据量及冷暖状态。
- **修复原则**：并行独立工作，合并重复工作，缩小同步范围，隔离可选依赖。只有证据指向计算、数据库或基础设施时才展开对应优化，不先堆缓存或增加索引。
- **验证维度**：关键路径与资源消耗、可选依赖挂起或失败、不同负载与缓存状态；确认提速没有破坏依赖或一致性。

## 二、状态与并发

- **核心约束**：每个结果属于仍有效的上下文，状态迁移与操作顺序符合业务约定。
- **失效机制**：旧结果覆盖新状态；并发重入产生重复操作；上下文变化后旧请求回填；取消、卸载或异常时遗留任务；共享锁被错误释放。
- **检查方法**：列出状态写入者、重复入口和生命周期边界，追踪异步结果的归属、顺序及失效条件；区分取消本地等待与撤销外部副作用。
- **修复原则**：采用上下文绑定、代次或序号校验、互斥、取消与清理；选择符合业务的并发策略，不把所有操作无条件串行化。
- **验证维度**：控制完成顺序，交错触发与取消，跨越上下文切换、重新进入及实例重建；断言最终状态、结果归属和副作用次数。

## 三、一致性与提交语义

- **核心约束**：关联数据满足同一业务不变量，外部副作用与提交确认的语义明确。
- **失效机制**：多次读取混合不同版本；局部更新破坏关联关系；部分提交被当作全部成功；同步失败被当作提交失败；未知结果被自动重试。
- **检查方法**：识别事务与快照边界、关联数据约束、权威确认来源、幂等保证及结果查询语义；检查错误处理是否混淆不同阶段。
- **修复原则**：保持事务、快照或版本协议；局部更新仅用于提交已确认、上下文未变、基线匹配且结果充分的情况；明确拒绝、已提交和结果未知分开处理。
- **验证维度**：交错读写、部分失败、提交后同步失败、响应丢失、重复触发与多实例竞争；检查真实持久化和返回语义。

| 权威提交结果 | 后续同步结果 | 正确语义与处理 |
|---|---|---|
| 已确认提交 | 成功 | 已提交且已同步 |
| 已确认提交 | 失败 | 提交事实不变，单独恢复同步 |
| 已确认未提交 | 不适用 | 返回真实拒绝原因，按业务规则决定重试 |
| 无法确认 | 任意 | 保持待确认，依靠权威结果或服务端幂等协议消除不确定性 |

普通读取暂时没有结果不能证明未提交。幂等键必须有服务端约束；客户端持久台账只能降低风险，不能替代服务端保证。防重约束须覆盖实际可再次触发的生命周期；当前能力不足时明确保留未解决边界。

## 四、身份与缓存

- **核心约束**：访问由可信身份与资源归属授权，缓存有明确归属、结构、有效期和失效条件。
- **失效机制**：从缓存推断权限；跨身份或上下文复用数据；临时身份读取失败被当作退出；身份变化后仍消费旧结果；缓存异常污染业务结果。
- **检查方法**：追踪服务端授权、身份来源、缓存键与结构、期限策略、失效传播及发布前核验；区分展示缓存与承担正确性约束的持久协议状态。
- **修复原则**：按可信上下文隔离缓存；身份失效清理私有数据并使旧结果失效；缓存解析或存储失败可降级，但必需的协议状态写入失败必须单独处理。
- **验证维度**：身份三分支、归属变化、过期或损坏缓存、存储不可用、晚到结果、跨生命周期恢复；客户端限制不能代替服务端权限验证。

| 可信身份结果 | 通用处理原则 |
|---|---|
| 有效身份 | 仅访问授权范围，按策略消费归属匹配且有效的数据 |
| 明确未认证或身份变化 | 使旧上下文失效，清理不再允许展示的数据 |
| 身份读取失败 | 标记身份待核验，不从缓存授予权限，不误判为明确退出 |

首次身份未知时不展示私有缓存；已有可信展示按业务策略决定是否保留为只读待核验。身份核验可使用可信会话状态与变化事件，不意味着每次状态更新都增加网络查询。

## 五、交互与可观测性

- **核心约束**：界面、返回值和观测信息准确表达真实执行阶段、结果及恢复方式。
- **失效机制**：反馈晚于操作开始；全局状态遮蔽局部可用结果；成功、拒绝与未知混用；异常被吞没；重试提示诱发重复副作用。
- **检查方法**：把用户或调用方可见状态映射到真实阶段，检查等待、部分可用、提交、同步、失败与待确认状态是否有明确转换及观测证据。
- **修复原则**：及时给出阶段反馈；拆分独立加载与错误边界；展示已知事实和可执行恢复动作；保留诊断信息而不泄露凭据或私有数据。
- **验证维度**：慢依赖、挂起、明确拒绝、未知结果和恢复；反馈应与数据和副作用一致，不能只改变文案或动画。

## 六、业务与运行边界

- **核心约束**：真实业务条件、输入范围、访问权限、资源生命周期和环境契约均被实现。
- **失效机制**：示例值冒充可信事实；缺失与零值混淆；外部结果未验证即产生副作用；分页、日期或规模越界；输入越过指令边界；资源清理遗漏；环境或接口版本假设失效。
- **检查方法**：对照权威数据与业务成功定义；追踪输入到查询、命令、输出或路径的边界；核对权限、分页、时区、取消、清理及实际运行配置。
- **修复原则**：保留真实数据和明确未知状态，验证前置条件，采用参数绑定与正确转义，限制越界输入，补齐资源释放与环境契约；不编造缺失能力或需求。
- **验证维度**：缺失、空值、零值、极值、末页、跨时间边界、依赖失败、越权与恶意输入、资源异常退出、环境差异；按证据选择必要场景。

## 通用验证原则

先复现失效机制，再验证修复后的约束。测试选择取决于本次改动影响，不机械扩张为所有类别的完整测试套件。

行为验证需观察结果、状态归属、持久化和副作用；静态检查与构建只能证明各自性质。既有测试全通过不能代表未覆盖的生命周期、并发或运行环境正确。

使用隔离依赖、测试数据或已授权环境。操作可在界面撤销，不代表外部副作用可无损撤销。无法安全验证或能力不足的部分明确报告限制。
