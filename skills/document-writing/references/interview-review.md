# 面试复盘细则

## 重点

- **目的**：把真实技术面、HR 面或模拟面试材料转为有依据的评价与改进建议。
- **分析与表达分开**：生成复盘时分析；只格式化已有复盘时保留既有结论。
- **证据独立**：现场回答、分析判断和改进答案清楚区分，复盘另存文件。

## 一、任务与材料

生成或重新分析复盘需要实际面试转写内容，可以是文件或用户提供的文本。
缺少原稿内容时先取得材料，不凭题目列表编造现场表现和评分。
只整理已有复盘的格式时不要求原稿，也不重新评分或补写分析。

简历、岗位 JD、面试类型、轮次、目标岗位、时间或批次是建议材料。
可提醒用户补充，但缺少时继续处理，在概览中说明具体分析范围。
未知的个人经历和公司内部信息不能靠推测填入。

面试概览中的日期、时长、面试官身份等直接填写明确的信息。
例如写“面试日期：2026-10-13”“面试官：团队负责人”，
不附用户确认、转写纠错等编写过程。信息表述沿用主 skill 的成文规则。
面试官的观点仍需明确归属，例如“面试官认为 AI 可以承担更多编码工作”；
候选人的反问只表示提问，不能写成公司已采用的流程。
术语或说话人澄清后，同步修正引用、分析和受影响的评分，移除过期的疑点；
仅纠正转写与排版，不代表现场回答质量提高。

默认输出 Markdown，用户明确要求时输出 HTML 或两者，不重复询问已确定格式。

## 二、分析流程与文件

1. 确认是生成、重新分析还是仅格式整理；检查已有材料及可读性。
2. 用户要求先清理，或原稿确实不可读时，使用 `transcript-refine` 的面试模式。
   本文件不维护另一份清理规则。原稿已清楚时直接分析。
   若环境缺少清理 skill，保留原稿，只分析可读内容并说明缺口。
3. 按原始顺序识别问题、追问、候选人回答和面试官表达的观点。
   结合原稿与清理稿中的定位，区分实际回答、合理归纳和改进建议。
4. 按下述评分及逐题规则分析，再形成短板、优先背诵材料和复习顺序。
   缺少足够回答内容时写明无法判断，不强行给档次。
5. 组织一次完整内容，再按用户请求渲染 Markdown、HTML 或两者。
   Markdown 读取主 skill 的 Markdown 规则及
   [复盘模板](../assets/interview-review.md)；
   HTML 额外读取 [HTML 规则](interview-html.md) 和其模板。
6. 新建 `<原名>-复盘.md` 或 `<原名>-复盘.html`，不覆盖原稿或清理稿。
   `<原名>` 是原始文件不含扩展名的名称；
   不因输入为清理稿而反复叠加“清理”后缀。
   用户指定路径优先；只有粘贴文本时按可辨主题命名。
   目标存在时使用不冲突的新文件名，明确要求更新已有复盘时才更新。

引用位置必须说明对应原稿还是清理稿，优先保留原稿时间戳或真实行范围。
位置无法可靠获得时省略并说明限制，不制造定位。
技术补充可使用可靠知识与可核查资料，来源不足或结论不确定时明确缺口；
补充知识不能包装成候选人实际做过的项目或现场已经讲出的内容。

## 三、评分标准

| 档次 | 含义 | 判定标准 |
| --- | --- | --- |
| 通过 | 当前回答基本能支撑面试官继续往下聊 | 回答切题，有清晰主线，关键事实可信，能讲出必要的背景、做法、结果或取舍 |
| 勉强通过 | 方向大体对，但存在明显扣分点 | 有部分有效信息，但结构松散、关键细节不足、指标/取舍/边界不清，容易被追问打穿 |
| 不通过 | 当前回答会显著损害面试评价 | 答非所问、概念错误、项目事实缺失、逻辑断裂、无法说明个人贡献，或暴露严重知识短板 |

评分维度：

- **切题性**：是否回答面试官真正问的问题。
- **结构性**：是否有背景、动作、结果、取舍或边界。
- **可信度**：项目经验方向是否有真实项目细节、指标、角色边界或落地证据；
  技术扩展方向是否有清晰定义、机制、边界和推理依据。
- **技术深度**：是否讲清原理、难点、方案比较或故障处理。
- **理念成熟度**：涉及流程、协作、趋势或职业判断时，是否有清晰观点、现实约束、
  判断依据、落地方法和反思，而不是泛泛而谈。
- **表达稳定性**：是否能让面试官听懂并愿意继续追问。

## 四、逐题复盘规则

所有问题统一放在 `## 二、逐题复盘`。每题内部根据回答质量决定详略。

每题标题直接使用面试官的问题本身，例如
`### 2.1 PostgreSQL 和 MySQL 的差异、为什么选 PostgreSQL`。

每题记录以下字段：

- **原文位置**：原稿中的行号、时间戳或段落编号；没有明确位置时可省略。
- **评价**：`通过` / `勉强通过` / `不通过`。
- **面试官考点**：说明这道题考察什么能力或风险点，不要复述题干。
- **面试官/公司视角**：记录面试官在交流中表达的观点、公司当前观念、团队偏好、
  业务约束或评价倾向；若原文没有体现，写“本题未体现明确的面试官/公司视角”。
- **回答方向**：可写 `项目经验方向` / `技术扩展方向` / `理念与协作方向` /
  `两者结合` / `多方向结合`。
- **现场表现**：概括原回答做得好的地方、暴露的问题、被追问时的状态。
- **项目经验方向**：有经验就写清真实项目背景、动作、结果和边界；
  没有就写“本次面试未体现对应项目经验”或“过往项目中未直接涉及”。
- **技术扩展方向**：技术问题无论是否有项目经验，都补充技术知识、原理机制、
  设计方案、优缺点、适用场景和追问方向。纯 HR 或理念问题不硬凑技术内容，
  使用适用的回答方向。
- **理念与协作方向**：当题目涉及工作流程、工程理念、AI 趋势、团队协作、
  职业判断、产品/业务理解或方法论交流时填写；不适用时可省略。
- **简单精炼版**：用于复习唤醒记忆，优先用短要点表达。
- **下次可这样答 / 详细面试版答案**：根据题目质量决定长度；能直接口头复述。

面试官/公司视角只记录转写稿中可观察到的信息或合理归纳，不要臆测公司内部事实。
它的作用是帮助复盘“对方真正关心什么”和“下次如何贴近对方语境表达”。

理念与协作方向不能空泛喊口号。需要说明观点、判断依据、真实工作方法、取舍边界，
以及下一次面试可以如何表达得更稳。

答得还可以的问题只做记忆唤醒：现场表现、简单精炼版、
下次可这样答可以控制在短要点，不生成长篇标准答案。

答得不好的问题必须补充：

- 原回答问题。
- 答不好原因。
- 类似情况作答策略。
- 简单精炼版答案。
- 详细面试版答案。

答不好原因要分析本质问题，例如没听懂考点、没有回应面试官视角、缺少结构、
缺少例子、概念错误、边界不清、经验不足但没有转入技术认识、表达过散或没有结论。

类似情况作答策略要给出下一次可复用的处理方式，例如先确认问题、先给结论、
对齐面试官/公司视角、用项目事实支撑、用技术原则补足、
承认经验边界后给学习认识或可落地方案。

详细面试版答案要能直接口头复述；不要把不存在的项目经历说成做过，
但可以写“技术上可以如何设计”“我学习后对这个问题的认识”“如果项目要补齐会怎么做”。
理念与协作类问题要补充清晰立场、判断依据、落地方式和边界，避免只写价值观口号。

## 五、短板卡片

每个短板使用固定字段：

- **面试暴露**：来自哪一题、哪段回答或哪类表达问题。
- **问题本质**：知识缺口、表达结构差、缺指标、缺 trade-off、缺故障复盘、
  可信细节不足等。
- **影响等级**：高 / 中 / 低。
- **对应评分影响**：导致哪些题从“通过”降为“勉强通过”或“不通过”。
- **需要补齐的知识**：后续应补的具体知识或材料。
- **下次回答抓手**：下一次回答时可直接使用的结构。
- **训练题**：1 到 3 道针对性训练题。

## 六、成文与自检

默认结构为重点、面试概览、逐题复盘、短板卡片、
下次面试优先背诵版、建议复习顺序。
题目默认按原顺序统一复盘，不另设“可复用回答素材”章节。
章节和字段按实际证据与适用性选择，不生成空章节；
缺少可观察的公司视角等必要说明，按逐题规则写明未体现。
模板只是布局起点，不是必须填满的表单。

- 是否基于真实材料评价，避免把追问、面试官观点与候选人回答混淆？
- 评分是否使用三档，并且有足够依据；仅格式化时是否保留已有结论？
- 每题是否有考点、视角、现场表现、适用方向及复习答案？
- 弱回答是否分析问题、根因和同类题策略，并给简版与口述详版？
- 理念与协作题是否有观点、依据、方法和边界，未硬套技术规格？
- 短板是否可追溯，包含影响、补齐内容、下次抓手和一到三道训练题？
- 面试时间或批次等有提供的信息是否保留，缺失信息是否明确？
- 是否新建复盘、保护原稿，双格式内容与字段顺序是否一致？
- 是否沿用主 skill 的标题编号、分段、强调和可读性规则？
