# Markdown 编写规则

所有 Markdown 成文任务读取本文件，并结合对应文档类型细则执行。
面试清理稿是证据整理，由 `transcript-refine` 处理。

## 通用格式

1. 全文只有一个顶层 `# 标题`，并以它作为第一个标题。
   保留原题含义；缺少标题时从明显的标题文本、
   文件名或首段主题推断。仍无法确定时用
   `# 待确认标题`，在重点中说明。
2. `## 重点` 只出现一次，紧接在顶层标题后，
   位于正文标题之前。使用 bullet 列表，每条以加粗的
   关键信号短语开头，接一到两句独立可读的说明；
   数量按内容决定。重点只能提炼已有信息，
   不编造事实、数字、状态或结论。
3. 正文标题按需设置，不生成空章节。`##` 使用连续的
   中文序号，如 `## 一、背景`；`###` 使用所属章节的
   编号，如 `### 1.1 现状`；`####` 使用
   `#### 1.1.1 原因`。同级递增，不跳号、不重复，
   只在需要时加深层级。
4. 关系或流程用图能明显改善理解时，先写一句图意说明，
   再给出带 `mermaid` 语言标记的代码块。
   已有代码块、表格除明显损坏或缺少必要格式外尽量保留；
   代码块不强制添加语言标签，表格保证正确和可读即可。

基本结构：

```markdown
# <标题>

## 重点

- **<关键信息>**：<来自文档的简短说明>。

## 一、<正文主题>

<正文>
```

## 段落与分点

所有文档类型都按内容关系组织段落和列表：

- 每个段落围绕一个主要主题展开。主题、论点或叙述阶段改变时，
  用空行分成新段；较长说明可按结论、原因、例子分别展开，
  避免把多个独立主题塞进同一段。
- 源码中的普通换行仍属于同一段；真正分段需要空行。
  不用机械地拆句或每句单独成段代替内容组织。
- 并列的规则、特性、职责、选项和注意事项使用 `-` 无序列表；
  有先后顺序或依赖关系的操作步骤、流程使用 `1.` 有序列表。
  连贯的解释和论证用段落展开，不把所有正文都变成列表。
- 每条列表项承载一个要点或步骤，先写核心内容再补解释。
  列表项较长时可以在项内分段，续行和后续段落保持正确缩进；
  只有存在明确的包含关系时才嵌套列表。
- 标题、段落和列表之间保留必要空行；较长的内容块按主题加小节，
  避免连续堆积大量列表项。

## 语义标识与强调

所有文档类型都按文字的含义选用标识：

- **加粗**：突出核心结论、关键规则、设计决策、限制条件，
  或术语表中的标准名称。优先加粗关键词和短语；
  不把整句、整段或每个列表项都加粗。
  `## 重点` 中每条 bullet 的关键信号短语保持加粗。
- **行内代码**：用于需要精确识别的技术文本，
  如字段名、函数名、命令、文件路径、配置值和接口路径。
  不用它强调普通概念或整句说明；
  介绍字段、函数时，同时解释名称含义与实际作用。
- **代码块**：承载多行代码、命令、配置和 Mermaid 图。
  不把普通说明段落放进代码块来突出显示。
- **引用块**：用 `>` 标识原文摘录，
  使引用内容与作者自己的解释清楚区分；保留来源依据。
- **链接**：连接资料来源、相关文档和共用术语定义；
  链接文字应说明目标内容，避免只有“点击这里”。
- **删除线**：用 `~~删除线~~` 标识明确已废弃的旧方案；
  当前有效的规则与方案正常书写。

标题、列表和表格负责组织内容，加粗提示优先阅读的位置，
行内代码标识应原样理解的文本。中文文档不默认使用斜体；
`==高亮==` 等扩展语法仅在目标阅读器明确支持且用户需要时使用。

### 加粗与标点边界

加粗是否生效取决于 `**` 内外相邻的标点、文字和空白。
当标点落在加粗内容的开头或结尾，且标记外紧接正文时，
可能无法形成有效的强调边界，直接显示原始星号。

- 默认只用 `**` 包住关键词，冒号、句末标点、外围引号和括号放在外面。
  保留原有文字及标点，只调整加粗范围。
- 短语内部有意义的标点保留，例如 `**读取、写入**`。
  已确认能正常渲染的写法无需机械改动，不把所有带标点的加粗判为错误。
- `**` 内侧不留首尾空格；短关键词与两侧标记作为整体安排源码换行。
  不用给所有加粗添加空格、改用 `__`、转义星号或插入不可见字符来修补。
- 技术名称自身包含标点时保持完整，按语义优先使用行内代码，
  例如 `C++`；确需加粗时调整周围句式，并验证实际渲染。
- 有目标阅读器预览时检查效果；否则可用 CommonMark 兼容解析器抽查，
  确认预期文字生成强调节点，而非只检查星号数量是否成对。

典型修正如下，源码放在行内代码中供对照：

| 有边界风险的源码 | 推荐源码 |
| --- | --- |
| `**重点：**正文` | `**重点**：正文` |
| `这段**“重点”**内容` | `这段“**重点**”内容` |
| `**（重点）**需要注意` | `（**重点**）需要注意` |

规则依据：[CommonMark 强调与加粗边界](https://spec.commonmark.org/0.31.2/#emphasis-and-strong-emphasis)。

## 源码可读性与换行

- 正文段落和列表项要便于在 Markdown 源码视图、窄窗口及差异视图中阅读。
  新写或整理时主动将过长的物理行换行，避免依赖水平滚动。
  默认以约 80 个显示列为参考（中文和全角字符通常占 2 列，
  英文、数字和半角符号通常占 1 列）；
  项目已有行宽约定或展示窗口更窄时，按实际情况调整。
- 优先在句号、分号等语义停顿处断行，不拆开词语、链接或行内代码。
  普通换行只用于整理源码；除非内容本身需要固定的显示换行，
  不添加行尾双空格或 `<br>`。
- 列表项可以跨多行，续行缩进到列表正文的位置。
  `## 重点` 中的每条 bullet 也遵循此规则，不能因一句话过长而写成单个超长物理行。
  例如：

  ```markdown
  - **组件分工**：网页负责计划与重置会话；
    服务侧负责调度和选择执行位置；
    本机与云端执行器分别承担任务执行。
  ```

- 长标题应精简；表格单元格无法安全地在源码中换行时，
  改用列表或小节承载长段说明。代码块按语言语法整理，
  不为满足行宽而破坏代码；长链接优先使用简短的链接文字。

## 旧文更新

- 即使只改动一小部分，也检查全文是否有单个顶层标题、
  紧随其后的唯一 `## 重点`，并让重点反映当前内容。
- 检查最终文档中的正文和列表物理行；对超长行按上述规则换行，
  保持原意与 Markdown 结构，不把一条列表拆成多条。
- 保留原意、已知事实、未决状态、正文措辞与标题深度；
  主要做必要的区块补齐、编号和轻量重排。
  编号只改变标题文字，不要求改变层级。
- 仅当多个 `#`、跳级标题或新增 `## 重点` 使正文
  错误归入重点之下，或用户明确要求重组时，
  才最小幅度调整层级。例如原文在 `#` 后直接使用
  `###` 正文标题时，将其提升到 `##`。调整后检查文内链接。
- 缺少某类型常见内容时，不按模板补写未知事实。
  必要信息缺失且影响任务完成时向用户确认；
  可继续处理的部分先完成，在交付说明中指出缺口。

## 格式自检

检查标题与重点的唯一性和顺序、编号连续性、正文与列表源码行宽、
段落主题和空行、列表缩进、语义标识、加粗与标点的渲染边界、
代码块、表格和 Mermaid。
内容与输出契约遵循主 `SKILL.md` 及命中的文档类型细则。
