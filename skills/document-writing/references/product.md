# 产品文档细则

适用于 PRD（产品需求文档）和功能说明。成文时遵循主 `SKILL.md` 的通用格式。

## 一、产品判断

新写或实质改写涉及产品方向、首版范围或需求验证的文档时，先明确做产品的目的。
其余问题按产品阶段和材料选用，把用户侧的回答落到一次具体使用。

| 问题 | 要明确的内容 |
| --- | --- |
| 1. 我们为什么做这个产品？ | 明确发起方的长期目的、本阶段的首要目标，以及继续投入的依据。 |
| 2. 第一批用户是谁？ | 用户角色、触发场景和当时想完成的任务。 |
| 3. 问题有多痛？ | 问用户最近一次遇到是什么时候、怎么处理、花了多久，以及问题发生的频率和代价。 |
| 4. 用户为什么会换用这个产品？ | 找出用户现在的做法或替代方案，比较结果、耗时和切换成本。 |
| 5. 第一版交付什么结果？ | 定义用户能完成的最小流程、可观察的结果和适用范围。 |
| 6. 用户怎么发现并开始使用？ | 说明从接触产品到首次获得结果的路径，检查理解、安装、注册或操作中的实际阻力。 |
| 7. 什么行为说明值得继续做？ | 定义用户首次成功和主动复用的行为，并结合阶段目标设定继续投入的条件。 |
| 8. 能否持续维护？ | 判断关键依赖变化、维护成本和可投入的时间。 |

第一个问题明确发起方希望得到的结果，后续问题明确产品给用户带来的价值。
按首要目标确定首版范围、推广对象和验证信号：

- **尽早获得收入**：明确谁会为什么结果付费，用实际付费或付费试用验证。
- **先积累用户**：观察目标用户能否独立上手、是否主动复用，以及是否出现共通的后续需求。
- **先积累影响力**：明确希望触达的人群，观察目标人群的关注、同行转发或主动合作。
- **积累作品或经验**：明确要走通的交付环节，以及能展示的成品或经验证的产品判断。

如果积累用户或影响力是为后续变现做铺垫，写清要积累什么、谁可能为什么结果付费，
以及出现什么信号后再验证付费。目的尚未确定时，记录待确认的选项及其决策影响。

有具体项目时，写清已有证据、假设和待确认项。优先选择一项缺少证据且会改变当前决策的假设，
说明用什么场景验证、观察什么行为，以及不同结果会怎样影响下一步。可让目标用户带来一次
真实任务，了解他们原来的做法，再观察能否独立完成及是否获得预期结果。
把拟定的样本量和成功门槛写为试验计划，把实际观察写为结果。

文档涉及推广前验证时，优先核对关键流程能否在真实环境中完成，
再观察目标用户能否独立上手并获得价值。

## 二、内容与组织

- `## 重点` 提炼功能目标、关键行为和限制条件，
  不把实现方案当成功能结论。
- 按已有材料选择章节：目标与范围、用户或使用场景、
  操作流程、功能行为、业务规则、边界情况、验收条件。
  章节可合并、调整顺序或省略，不生成空模板。
- 只需要把功能描述清楚。技术架构、数据库、接口等
  是否已经设计好，不影响产品文档成立；
  不要为了“完整”补造技术方案。
- 未确定的产品规则保持待确认状态。已有共享术语表时，
  引用相应定义，不另写可能冲突的定义。

## 三、商业化独立成文

PRD 中涉及商业模式、套餐定价、收费和计费策略等内容时，
将这些内容单独保存为商业化 Markdown 文档，
并读取 [商业化细则](commercialization.md) 组织内容。
没有商业化材料时，不创建空文档。

PRD 链接到商业化文档；付费或套餐影响功能行为时，
PRD 描述相应的使用限制、权益判断和用户提示，
具体商业策略与收费规则以商业化文档为依据。
两份文档相互引用，避免重复维护价格和套餐信息。

## 四、与其他文档的关系

ROADMAP 可链接本文档以展开某项特性；
设计文档可引用本文档作为实现依据。
本文档不替设计文档规定实现。

## 五、场景检查

来源只有“用户可创建清单，并可删除自己的清单”时，
可描述这两项功能行为；不要写入数据库表、API 或权限实现。

同一份材料同时包含功能需求与套餐价格时，
功能需求留在 PRD，价格及收费规则整理到独立商业化文档，
两份文档使用链接关联。
